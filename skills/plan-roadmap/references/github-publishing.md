# GitHubへの反映

この手順は作成・更新が依頼されたときだけ使う。下書きから外部操作へ移るための自動許可ではない。

## 実行前

1. リポジトリ、可視性、使う認証、既存Issueとテンプレートを確認する。作成する親・子、再利用するIssue、更新差分を整理する。
2. 最新のIssueを検索・再取得し、タイトルだけでなく目的・受入条件・状態を照合する。既存Issueが一部を満たす場合は不足分だけ提案する。取得できない状態で重複なしと断定しない。
3. 対象・本文・操作が承認範囲に含まれることを確認する。変更された前提や共有範囲は再確認する。未決定の後続は、親に条件付きの候補として残せる。
4. 利用可能なGitHubコネクタ、公式API、CLIの対応機能を確認する。使えると確認していないコマンド・オプションを作らない。既存の認証を使い、新たな認証・権限設定を勝手に行わない。

## 作成とリンク

- 確認済みの親があれば再利用する。なければ親を作成し、返されたID・番号・URLを記録して再取得する。
- 子は承認された分だけ一つずつ作成し、仮IDとの対応を記録する。実行記録は作業用ファイル等に置き、機密を公開リポジトリへ保存しない。
- GitHubの**ネイティブなsub-issue関係**を対応ツールで設定し、親と子を再取得して確認する。親本文のチェックリストやリンクだけを「sub-issue設定済み」と呼ばない。
- 着手順は別途、利用可能ならGitHubの依存関係（blocked by / blocking）に設定して確認する。親子関係だけでは依存関係にならない。
- ネイティブな親子・依存関係を設定できない場合、本文に確認済みURL・関係・理由を明記し、「本文リンクのみ、ネイティブ設定は未実施」と報告する。承認範囲の下書き・作成は残せるが、設定済みとは言わない。
- 最後に親の本文を実在URLへ更新し、作成・再利用・未反映を照合する。ラベル・担当・Milestone・Projectは承認範囲でのみ設定する。

## 失敗・再開

- timeout等で作成結果が不明な場合は、まず作成時刻・本文・実行記録を使って再検索する。存在確認が終わるまで同じIssueを再作成しない。
- 一部だけ成功したら、そのIDを保存し、未実行分と結果不明分を分ける。成功済みを最初から作り直さない。リンク失敗を理由にIssueを作り直さない。
- 権限拒否、競合、結果を照合できない状態では、その操作を止める。拒否を別ツールで迂回しない。確実に未実行と分かり原因が解消した場合だけ、承認範囲で限定的に再試行する。
- 既存Issueの更新前には最新本文を読み、他者の変更・コメントを消さない。範囲外の変更が必要になったら確認する。

## 完了報告

親URL、子URL、ネイティブな親子・依存の設定結果、本文リンクだけの箇所、未反映と理由、次にユーザーが判断することを短く示す。Issueの作成は仕事の実施・成果達成ではない。
