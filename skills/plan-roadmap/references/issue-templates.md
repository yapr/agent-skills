# Issueの型

既存のIssueテンプレートを優先し、以下の情報を必要な場所にまとめる。空欄を埋めるために事実を作らない。小さな案件では項目をまとめ、重複説明は親への参照にする。

## 親Issue: ゴールとロードマップ

```markdown
# [達成したい状態]

## 目的と成功条件
- 対象・現状・困りごと:
- 目指す状態:
- 成果指標 / 現状値 → 目標値 / 測定元・方法 / 測定期間:
- 根拠: ユーザーとの合意、既存Issue、確認した事実
- 対象範囲 / 今回やらないこと:
- 期限と理由 / 使える時間・人・予算:

## 道筋
1. [マイルストーン]: 成果、次へ進む条件、なぜ先に必要か
2. [マイルストーン]: 成果、次へ進む条件、前段とどうつながるか
3. [成果の確認]: 検証方法、目標未達なら見直す内容

## Issue構成
- D1 [決めること]: 判断する問い、時間上限、後続への影響
- I1 [一つの成果]: 対応するマイルストーン、着手条件
- V1 [成果検証]: 対応する成功条件、着手条件
※ 作成前は仮ID。作成後は確認済みURLに置き換える。

## 依存と分岐
- D1 → I1: [何が決まれば、何を始められるか]
- [別案を選んだ場合の道筋 / 並列に進められる範囲]

## 未確定と見直し
- 合意済み / 提案 / 未確認:
- リスク、判断する人、次の判断日・条件:
- 目標変更・縮小・中止の条件:
- 完了条件: 必要な成果の証拠と、最終的に確認する人
```

親の完了は子Issueの件数やチェック数だけで判断しない。実装完了後に観測が必要なら、成果検証まで親を追跡する。目標未達で終了するときは、未達の証拠と終了判断を区別して記録する。

## 調査・意思決定Issue

```markdown
# [比較・検証して決めること]

## この判断が必要な理由
- 親・マイルストーン:
- 後続で止まっていること:

## 問いと調べる範囲
- 判断したい問い / 現時点の仮説 / 根拠:
- 比較対象・評価軸 / 調べないこと:
- 必要なデータと取得方法:

## 成果物と受入条件
- [ ] 比較結果に根拠、条件、限界が記載されている
- [ ] [選定基準]に照らし、推奨案と採らない理由を説明できる
- [ ] 判断する人が、採用・不採用・追加調査を記録できる材料が揃う
- 確認方法 / 証拠の置き場所:

## 進め方と判断
- 担当候補 / 必要工数・見積根拠 / 時間上限:
- 期限または起点と期間 / 判断する人:
- 着手条件 / 後続Issue:
- 採用・不採用の基準:
- 時間内に結論が出ない場合: 残る不明点、暫定判断、再調査の要否を記録
```

調査結果の提出と、その結果を採用する判断は別。担当者・判断者が違えば、後続の着手条件に判断の記録を含める。調査Issueの完了を実装方式の承認とみなさない。

## 実行・成果検証のサブIssue

```markdown
# [検証可能な一つの成果]

## 目的
- 親 / 対応するマイルストーン:
- この成果がゴールにつながる理由:

## 範囲
- 実施すること / 成果物:
- 実施しないこと:

## 受入条件と検証
- [ ] [対象・条件・観測結果から、第三者が合否を判定できる条件]
- [ ] [必要なら例外・失敗時の条件]
- 確認手順 / 測定元・対象・母数・期間 / 証拠の置き場所:

## 実現性と期限
- 担当候補・必要な能力:
- 工数の見積幅 / 根拠 / 確保できる時間:
- 期限、または[先行Issueの完了]から[期間] / 見直し条件:
- 着手条件と依存先 / 依存の理由 / 後続:
- 未確定事項と、その解消方法:
```

「使いやすくする」「最適化する」「調査する」は、そのままでは受入条件にならない。一方、根拠のない数値や日付を足してSMARTらしく見せない。二値の成果なら、例えば「指定の入力で期待したCSVが生成され、固定サンプルとの比較が一致する」のように検証方法を具体化する。
