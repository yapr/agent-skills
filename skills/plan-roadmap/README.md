# plan-roadmap をローカルで試す

目的を相談しながら、GitHubの親Issue・調査Issue・SMARTなサブIssueの案を作るSkillです。まず架空の題材で試し、道筋に納得してから実際のリポジトリで使えます。

## できること

- 不足している目的・制約を少しずつ聞く。
- 「なぜこの順番なのか」を説明したロードマップを作る。
- 方針が未定なら、比較や小さな実験で決めるIssueを先に置く。
- 各Issueの成果・受入条件・実現性・期限・依存関係を整理する。
- 依頼された範囲だけGitHubへ反映する。下書きだけでも使える。

このPRがマージされるまでは、以下のブランチから試してください。マージ前の `main` にはこのSkillはありません。

## 1. 準備

以下はmacOS / Linuxのターミナル向けです。作業用フォルダの中にSkillのコピーと練習用フォルダを作ります。すでに同じ名前のフォルダがある場合は、別の場所・名前を選んでください。

- GitとNode.js / npmが必要です。`git --version`、`node --version`、`npm --version` で確認できます。
- Codex CLIを導入し、通常のサインインを済ませておきます。`codex --version` で起動できるか確認します。
- 下書きの練習ではGitHubの書込権限は不要です。認証情報をSkillのファイルやプロンプトへ貼り付けないでください。

```sh
mkdir roadmap-playground
cd roadmap-playground

git clone --branch dot/plan-roadmap --single-branch \
  https://github.com/yapr/agent-skills.git
SKILLS_SOURCE="$(pwd)/agent-skills"

mkdir sandbox
cd sandbox
git init

npx --yes skills@1.7.4 add "$SKILLS_SOURCE" --skill plan-roadmap -a codex -y
```

`npx` は初回にCLIを取得するため、ネット接続が必要です。上のコマンドは練習用フォルダ内への導入で、`-g` による全体への導入はしません。

次で入口と参照ファイルがあることを確認できます。

```sh
test -f .agents/skills/plan-roadmap/SKILL.md
ls .agents/skills/plan-roadmap/references
```

マージ後に最新版の `main` を使う場合は、別の練習用フォルダで次の導入方法も使えます。これはマージ後の手順で、このPRではリモートの `main` からの導入は未検証です。

```sh
npx --yes skills@1.7.4 add yapr/agent-skills --skill plan-roadmap -a codex -y
```

## 2. 起動して、短いやり取りを試す

`sandbox` フォルダ内で起動します。

```sh
codex
```

起動後、以下を貼り付けてください。ターミナルのコマンドではなく、Codexへのメッセージです。

```text
$plan-roadmap を使ってください。
これは架空の練習です。外部サービスの参照・作成・更新はしないでください。
社内の月次レポートを作る手間を減らしたいです。
何から進めるか相談し、ロードマップの親IssueとサブIssueの本文案を作りたいです。
分からないことは先に少しずつ聞いてください。
```

最初は、困りごと・成功条件・使える時間など、計画に必要な質問が出る想定です。既に材料が十分なら、聞き直さず案を作る場合もあります。

質問への回答例です。実際に聞かれた内容に合わせて使ってください。

```text
直近3回の準備は各90分でした。同じ20項目を欠落・重複なく揃え、
次の2回で準備が各30分以内になることを目標にします。
自分が週4時間使えます。追加課金はしません。
APIから取るかCSVを読み込むかは未定なので、まず比較したいです。
今回は下書きだけ。担当・工数・期限は提案として示してください。
```

見たい出力は次のとおりです。

1. 目標と、達成できたかを確かめる方法
2. 取り込み方の比較 → 一回分の出力と照合 → 2回の実測、という道筋と理由
3. 比較・判断を行うIssueの案
4. 一つずつ検証できる実行・成果検証Issueの案と依存関係
5. 未確定事項と、次に自分が判断すること

出力は毎回同じ文章になるものではありません。[架空の分解例](references/example.md)と比べて、目的から成果検証までつながっているかを見てください。未合意の期限や担当が確定扱いなら、「そこは提案のままにして」と修正できます。

## 3. 実際のプロジェクトで使う

練習後、対象リポジトリのフォルダで同じ導入コマンドを実行し、そのフォルダで新しく `codex` を起動します。既に進行中の会話で認識されない場合も、まず新しい会話で確認してください。

```text
$plan-roadmap を使って、[実現したいこと]への道筋を作ってください。
対象は [owner/repository] です。
関連するIssueは [確認済みのURL]、制約は [期限・使える時間・予算など] です。
既存のIssueを確認し、重複を避けてください。
まずヒアリングと本文案まで。GitHubへの書込みはまだしないでください。
```

スキル名を認識しない場合は、導入した同じフォルダを開いているか確認します。次のようにファイルを指定しても試せます。

```text
.agents/skills/plan-roadmap/SKILL.md を読んで、その手順でロードマップを作ってください。
まずヒアリングと本文案までにしてください。
```

## 4. 納得したらGitHubへ反映する

対象リポジトリに書き込めるGitHub接続が必要です。下書きには接続不要ですが、既存Issueの調査・作成・親子関係の設定には、それぞれ対応するツールが必要です。

作成を依頼する例です。自分の案で使われている仮IDに置き換えてください。

```text
この案で進めます。[owner/repository] に親R1と子D1・V0を作成し、
親子関係を設定してください。承認した本文を使ってください。
I1は調査結果を見てからなので、まだ作成しないでください。
担当割当・ラベル・Milestone・Projectの変更はしないでください。
```

「本文にリンクがある」ことと「GitHubのsub-issueとして紐付いている」ことは別です。最後の報告で、作成URL・親子設定・依存設定・未反映事項を確認してください。対応ツールがなければ本文リンクまでに留まり、未設定であることが報告されます。

途中で止まった場合は、新しく同じIssueを作る前に結果を確認します。

```text
前回は親と一部の子Issueまで作成した可能性があります。
まず実在するIssueと前回の結果を照合し、重複を作らず未完了分を教えてください。
```

## 検証した範囲

| 項目 | 確認状況 |
| --- | --- |
| YAML形式・名前・参照ファイル | 形式検証とリンク確認を実施 |
| Codex用ファイルの導入 | Linux x86_64、Node.js 24.22.1、npm 11.9.0、skills CLI 1.7.4で、隔離した一時プロジェクトへ導入・内容一致を確認 |
| Codex CLIの存在・起動コマンド | 検証環境の0.167.0-alpha.4で `--version` / `--help` を確認 |
| 対話と計画の内容 | 架空の題材を使ったオフラインの対話・計画出力で確認。詳細はリポジトリの[確認ケース](../../tests/plan-roadmap.md) |
| ユーザーのローカル環境での対話起動 | 未検証。上の手順で確認する対象 |
| Codex CLIからモデルを呼び出す一連の試験 | 未実施。対話の検証はCLI起動試験とは別 |
| GitHub上のIssue作成・親子・依存の設定 | 未実施。テストで実Issueは作成していない |
| Claude Code等、Codex以外のエージェント | 未検証 |

Skillは実行権限を追加せず、GitHub接続も自動設定しません。導入できたことと、すべての外部操作ができることは別です。
