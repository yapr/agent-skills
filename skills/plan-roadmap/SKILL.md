# 納得できるロードマップを作る

「なぜこの順番で進めるとゴールに届くのか」を説明できる計画にする。タスクを列挙するだけで終えず、目的、根拠、意思決定、成果の確認までつなぐ。会話とIssueは読者に合わせ、指定がなければ簡潔な日本語で書く。

## 1. 現状を読み、必要なことだけ聞く

対象リポジトリ、既存Issue・PR・ロードマップ、Issueテンプレート、リポジトリのルールを許可された範囲で確認する。同じ成果を扱うIssueがあれば再利用候補にする。読めない情報は「未確認」であり、「存在しない」と扱わない。

既に答えがあることは聞き直さない。不足のうち、道筋を変えるものから一度に2〜4問程度を聞く。答えにくければ選択肢や仮案を添え、ユーザーの返答を待つ。チェックリストを埋めるための長い質問票にしない。

- **目的・成果:** 誰の何が変わるか。何をもって成功とするか。現状値、目標値、確認方法はあるか。
- **範囲・制約:** 今回やること・やらないこと。期限の理由、使える時間・人・予算、守るべき仕様や運用は何か。
- **不確実性:** 分かっている事実、仮説、未決定の選択肢は何か。何が分かれば次を決められるか。
- **進め方:** 最初に価値を確かめられる単位、優先順位、判断する人。GitHubは下書きか作成・更新までか。

返答を短く要約し、合意済み・提案・未確認を分ける。ゴールと主な制約が分かれば計画案へ進む。重要な未回答を勝手に補完しない。回答待ちの間に出す案や「仮で進めて」の案は仮説として示し、確定計画にしない。

## 2. ゴールから道筋を組み立てる

ゴールから逆算し、「成果を確かめる → 必要な実装・運用 → その前に決めること」の順で必要条件を探す。実際の実行順は前提を解消する順に並べる。工程名より、各段階を終えると何が可能になるかを示す。

各マイルストーンに、狙う成果、次へ進む条件、根拠、主なリスクを付ける。重要な選択肢があれば、推奨案と代替案の得失、採らない理由を示す。最短の価値検証を先に置き、依存しない仕事だけを並列にする。

成果指標と作業完了を分ける。「機能を公開した」は「利用者の問題が解決した」の証拠ではない。測定期間・母数・測定元を示し、未計測なら測定準備を先に置く。数値目標や期限を創作せず、提案値には根拠と要合意の表示を付ける。

### 方向性が決まっていない場合

実装を先に約束せず、調査・比較・小さな実験で**判断を可能にするIssue**を置く。調査には、答える問い、比較軸、成果物、時間の上限、判断する人、採用・不採用・追加調査の基準を設ける。「調べる」だけを完了条件にしない。

後続は判断結果による条件分岐として示す。判断前の詳細な実装Issueを大量に確定・作成しない。今すぐ実行できる分を具体化し、遠い工程は成果と見直し条件を保つ。調査で実現困難と分かった場合の縮小・中止も妥当な判断として扱う。

## 3. SMARTなIssueへ分ける

下書き時に[Issueの型](references/issue-templates.md)を読む。親Issueにゴールと全体の道筋を置き、子Issueには一つの成果または意思決定を割り当てる。粒度に迷うときだけ[架空の分解例](references/example.md)を参照する。

- **S / 具体的:** 対象、成果物、やること・やらないことが明確。
- **M / 測定可能:** 第三者が証拠で判定できる受入条件と確認方法がある。数値が不要な成果は、再現可能な合否条件でよい。
- **A / 実現可能:** 担当候補・必要な能力、工数の見積幅と根拠、使える時間、依存先が釣り合う。無理なら範囲・順番・期限の調整案を出す。
- **R / 目的に関連:** どのマイルストーンに必要で、ゴールへどう効くかを説明できる。
- **T / 期限付き:** 合意した期日、または「先行Issue完了からN営業日以内」など起点の明確な期間・見直し日がある。期日と工数を混同しない。

担当・工数・期限が不明なら「提案」「未確定」と残し、SMARTを満たしたとは言わない。不明点を解消する次の行動を示す。誰かへの割当や期日の確約は、計画案だけで実施しない。

草案には `R1`、`D1`、`I1` などの仮IDを使う。実在しないIssue番号・URLを作らない。**親子関係**は作業範囲、**依存関係**は着手条件として別々に表す。各依存に理由を付け、循環・欠落・不要な直列化がないか確認する。承認や実測待ちも依存として残す。

## 4. 説明して、合意範囲を確かめる

まず次を短く示し、必要な箇所からIssue本文を読めるようにする。

1. 目指す状態と成功の確認方法
2. 道筋と、その順番にする理由
3. 最初に決めること・着手できること
4. 親子Issue案、依存関係、期限・担当の確定状況
5. 未確認事項、リスク、見直しの条件

「この道筋でよいか」と「GitHubで何を作成・更新するか」を区別する。計画作成だけの依頼なら下書きまで。対象・内容・操作を含む作成依頼が既にあれば再承認を増やさず、その範囲で進める。重要な前提や対象が変わったときは再確認する。

## 5. 承認済みの範囲をGitHubへ反映する

実行時だけ[GitHubへの反映手順](references/github-publishing.md)を読む。対象リポジトリと公開範囲、作成・更新する親子Issue、既存Issueの扱いを確認する。本文の機密情報、個人・顧客情報、非公開URLを共有可能な範囲に絞る。

計画の承認を、実装・マージ・デプロイや第三者への依頼の許可に読み替えない。ラベル、担当割当、Milestone、Project変更、既存Issueの終了も依頼範囲に含まれる場合だけ行う。Skill自体はアクセス権を与えず、拒否された操作を別手段で迂回しない。

最後は「下書き」「作成済み」「親子関係設定済み」「依存設定済み」「未反映・未確認」を区別し、確認できたURLと次の一手を報告する。調査や節目の結果で前提が崩れたら、影響する目標・後続Issue・期限を見直し、変更理由を残す。自動監視や定期更新は別途依頼された場合だけ設定する。
