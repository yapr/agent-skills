# GTM + GA4 セットアップ

標準はサイト → GTM → Google tag / Analytics destination → GA4。直接のgtag.jsやGoogleAnalyticsコンポーネントは併用しない。既存方式を無断で外さず、移行案を先に作る。

## 1. 対象と既存設定

[導入・dry-run](README.md)と[実行・検証手順](references/setup.md)を読む。対象URL、フレームワーク、GA4/GTMアカウント、既存ID、対象環境を明示指定→サイト台帳の順で確認し、不明な必須値だけ聞く。URLはドメインだけで所有権やアカウントを推測しない。秘密ファイルを探し回らない。

リポジトリのルールと関連Skillを確認する。既存の認証・許可された読取操作で、Property / Web Stream / Container / Workspace / タグ・トリガー・同意設定を全ページ取得する。サイトの共通テンプレート、プラグイン、CMP、実際のDOM・通信も確認する。取得不能・部分取得・権限不足は「未確認」で、存在しないとは扱わない。

## 2. 計画

取得結果を秘密情報のないローカル入力へ整理し、`scripts/plan.py --input <file> --dry-run` を実行する。補助ツールはオフラインの計画だけで、実アカウントの検出・設定・計測検証は行わない。

既定は既存リソース優先、1サイト1測定先・1挿入元、追加広告・User-ID・独自イベントなし。複数送信先が意図された構成なら自動統合せず確認する。既存ID・紐付け・タグの意味を照合し、表示名一致だけで再利用しない。Google側の同意・契約、CMPと送信項目の方針が未確定なら残件にする。

## 3. 承認後の実行

変更ごとに対象リソース・差分・影響・戻し方を提示する。リソース作成、Workspace変更、サイト編集の権限を分け、承認された操作だけ対応ツールで実行する。GTM公開・deploy・本番変更・課金・認証作成や拡張・OAuth承認・アクセス付与は別の個別承認が必要。セットアップ依頼だけでこれらを実行しない。

実行直前に再取得して計画の差分を更新する。既存なら作成せず、不足分だけ扱う。ID・Workspace path・fingerprint・操作結果を秘密情報なしで記録する。timeout後は結果不明として再一覧取得し、再作成しない。競合・403・部分失敗は停止。拒否を別ツールで迂回しない。

既存CLIはバージョン・ライセンス・公開等の副作用・dry-runの実態を先に確認する。公開を内包する一括コマンドは使わず、工程別に制御できなければ手動手順へ切り替える。認証不足を成功扱いしない。

## 4. 結果

「計画済み」「Workspace設定済み」「サイト設置確認」「GTM公開確認」「GA4受信確認」を分け、対象環境・検証時刻・根拠を残す。計画やタグの存在だけで「設定完了」にしない。未実行・要手動対応・失敗を明記し、短い日本語でID・変更・検証・残件を報告する。秘密・顧客・個人情報、実サイト台帳は公開コードやPRへ転載しない。
