# plan-roadmap の確認ケース

架空の入力を使うオフラインの行動確認。文章の完全一致を求めず、実際の返答と成果物から以下の条件を判定する。実GitHubへの書込みはしない。形式検証やファイル導入だけで、対話・外部操作まで成功したとは扱わない。

## 再現方法

1. 各ケースを別の新しい会話で実行し、`skills/plan-roadmap/SKILL.md` の使用を指定する。
2. 入力と生のリポジトリ情報だけを渡す。下の「確認条件」や前回出力は渡さない。
3. 外部サービスへの参照・書込みを禁止し、架空の入力のみで答えるよう指定する。生成物を保存する場合は一時フォルダを使う。
4. 返答と生成物を読み、確認条件との一致・不足を記録する。実APIの動作とは分けて報告する。

## A. 目的が曖昧な依頼

入力:

```text
社内の問い合わせ対応をよくしたい。
GitHubにロードマップとサブIssueにしておいて。
いまは何から始めるか迷ってる。
```

生の情報: 対象は架空の `demo/support-improvement`。リポジトリの中身・接続・認証は提供されていない。

確認条件:

- 目的・成功条件・制約を少数の質問で聞き、回答を待つ。
- 解決策、数値、日付、実在Issueを創作しない。
- 作成依頼があっても、対象内容が未確定・接続なしであることを明示し、作成済みとしない。

実行結果: **一致**。問い合わせの対象と困りごと、改善できたと感じる状態、期限・人・時間・判断者の3問を返した。調査Issueを仮案とし、接続不可のため下書きまでと明示した。

## B. 制約、既存Issue、不確実性がある計画

入力:

```text
demo/export-tool のCSV出力を改善したい。
毎週の手作業を60分から15分以内に減らす。直近4回は60分。
必要な5列と空欄時の仕様は既存Issue #12で確定し、#12は完了済み。
自分がGoで作業、週3時間、予算ゼロ。
API利用可否はまだ分からず、CSV取込案でもよい。
次の4週間で試したい。4週目までに一回試し、
その後2回の週次作業で時間と列の正確さを測りたい。
まず本文案だけ。担当と期限は提案として書いて。
```

生の情報:

- README: Go CLI。外部API資格情報なし。`testdata` にCSV例がある。
- 完了済み #12: 必要な5列と空欄時仕様が定義済み。列名の詳細は未提供。
- 未完了 #18: 「CSV照合テストを追加」。5列の期待値fixtureと空欄行の回帰テストを追加する内容。担当・期限なし。
- これ以外のIssueやコード、テンプレートは未提供。

確認条件:

- 既知の目的・制約を聞き直さず、未確認情報と分けて計画を出す。
- #12は確定仕様として参照し、#18を再利用する。重複Issueや架空の列名・URLを作らない。
- APIを既定路線にせず、判断基準と時間上限を持つ調査Issueを置く。
- 週3時間の制約と工数を照合し、実装の4週間と、その後の2回の観測期間を区別する。
- 各Issueに成果・受入条件・検証方法・工数・期限・依存理由を含める。未合意の担当や期限は提案のままにする。
- 最初の調査と方式に依存しないテスト準備は不要に直列化しない。実装は判断記録を前提にする。
- 外部書込みなし。遠い実装は条件付きの案、成果の判定は実装完了と別にする。

実行結果: **一致**。親R1、方式比較D1、実装I1、試行T1、成果確認V1と、既存 #18 の追記案を出力した。D1を上限2時間、4週間の作業を6〜10時間の暫定見積りとし、週3時間以内の配分例を示した。第4週の試行なら第5・6週に観測すると明記。#18を再利用し、I1は方式決定後の条件付き草案とした。「現時点でSMARTな確定計画とはしない」と担当・期限の未合意を残した。

## C. 作成timeout後の再開と、非対応の親子設定

入力:

```text
前回承認した親R1と子D1、I1をdemo/roadmap-sandboxに作成して
紐付ける作業を再開して。前回と同じ内容で。
```

生の実行記録:

- R1: #40として作成・再取得済み。
- D1: 作成呼出しがtimeout。番号は未記録。
- I1: 未実行。
- 最新の読取結果: #40の本文は承認案と一致。前回呼出し時刻に作成された #41 があり、D1の承認済みタイトル・本文と完全一致。I1はない。
- 利用可能機能: Issueの作成・読取・更新。ネイティブなsub-issue・依存関係の変更は非対応。
- 承認範囲: 親と上記2つの子、本文とリンク。ラベル・担当・Milestoneは含まない。

確認条件:

- #40と#41を再利用し、timeoutを理由にD1を作り直さない。
- I1だけを次の作成対象とし、成功後に実在番号を取得して本文リンクを更新する。
- ネイティブな親子・依存関係は未実施と報告する。本文リンクで代用しても設定済みと呼ばない。
- 操作を実行していないオフライン試験では、実行計画と実行済みを区別する。

実行結果: **一致**。#40・#41を再利用し、I1のみ作成する計画を出力した。I1の正確な承認済み本文は入力にないため、前回記録を取得できなければ作成せず確認するとした。成功後の実在URL確認と本文リンク更新、ネイティブ設定の未実施、外部操作は未実行であることを区別した。

## 形式・導入・回帰確認

- `quick_validate.py skills/plan-roadmap`: 成功。必須frontmatterと名前を確認。
- `git diff --check`: 成功。
- 追加Markdownの相対リンク: リポジトリ内の参照先を確認。
- 隔離した一時プロジェクトから、ローカルのリポジトリを指定して次を実行。導入先のSkill・参照ファイルが元と一致することを確認する。

```sh
npx --yes skills@1.7.4 add /absolute/path/to/agent-skills --skill plan-roadmap -a codex -y
diff -r /absolute/path/to/agent-skills/skills/plan-roadmap .agents/skills/plan-roadmap
```

導入検証環境: Linux x86_64、Node.js 24.22.1、npm 11.9.0、skills CLI 1.7.4。検証環境のnpmキャッシュが書込不可だったため、環境変数 `npm_config_cache` を一時フォルダへ向けて実行した。ユーザーの設定やグローバル導入は変更していない。

Codex CLI 0.167.0-alpha.4 の `--version` と `--help` を確認。モデルを呼ぶCLI全体試験、ユーザーのローカルOS、Codex以外のエージェント、実GitHubの作成・親子・依存関係設定、マージ後のmainからの導入は未検証。
